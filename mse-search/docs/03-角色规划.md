# 03 角色规划 —— 角色定义、授权矩阵与数据权限

> mse-search 的角色与授权设计。权限点 id / code 见 [02-权限规划](02-权限规划.md)，功能点含义见 [01-功能规划](01-功能规划.md)。
> **重要差异**：mse-mes 等工程随种子 SQL 提供角色；**mse-search 未提供角色种子**（`db/mysql/` 三个脚本均无 `sys_role` 系插入）——本文角色清单为**建议角色（规划）**，由租户管理员在基座「角色管理」按本文矩阵手工配置，或后续以版本化脚本固化（见第七节）。

## 一、角色模型说明

1. **页面全为租户端**：六个管理页面 `menu_scope=2`，授权发生在**租户域**（套餐勾选为上界 + 角色授权）；子应用注册 `side=3` 双端，平台端仅经分组目录（480）单菜单项进入，且平台域权限集不含 4201-4211——平台侧只有平台超管（`*`）可运维平台自有目录（tenant 0），不设平台角色。
2. **租户超管不依赖角色**：`sys_user.super_admin=1` 的租户管理员天然拥有套餐域内全量权限码；本清单建议角色面向**分工**需要（搜索运维与搜索治理分权）。
3. **搜索使用零门槛**：`/search/api/*` 登录即可——**普通用户不需要任何 search 权限点、不需要被授予任何菜单**即可使用基座顶栏搜索与首页搜索卡片；能搜到什么完全由源级三层过滤裁定（第六节）。这是本产品与一般「菜单+按钮」业务工程的根本区别。
4. **角色受套餐裁剪约束**：即使授予 search_admin，其权限也以租户套餐勾选的 search 菜单（481-487）为上界。
5. **搜索引擎管理员 ≠ 租户超管**：search_admin 只管搜索域（源目录/任务/索引/字段），不涉及用户、角色、系统管理等基座能力。

## 二、角色清单（3 个，建议角色——无种子，落库需固化）

| 角色（建议编码） | 名称 | data_scope | 定位 | 涵盖权限点 |
| --- | --- | --- | --- | --- |
| `search_admin`（建议） | 搜索引擎管理员 | 1 全部 | 搜索域全量管理：源目录/调参/字段配置/任务/索引/搜索测试/租户搜索配置 | 4201-4211 全部 |
| `search_operator`（建议） | 搜索运维员 | 1 全部 | 日常运维：任务触发、索引运维、搜索验证，不改源目录与字段配置 | 4201（只读）+ 4203-4208 |
| `search_viewer`（建议） | 搜索查看员 | 1 全部 | 只读审计：看目录/任务/热词/索引水位，不可变更 | 4201 / 4203 / 4205 / 4207 / 4210 |

> 说明：本产品为**基础设施型服务**，操作对象是「源目录与索引」而非业务单据，行级 data_scope 无实际意义——三个建议角色一律取 data_scope=1（全部）；真正的数据边界由第六节三层过滤在**查询侧**强制注入，与操作者角色无关。

设计要点：

- **治理与运维分权**：字段配置（4209）与租户搜索配置保存（4211）影响索引 mapping 与检索行为，收归 search_admin；运维员只触发任务与运维索引。
- **搜索测试给运维员**：推文档/过滤对比是排查「搜不到」的第一手段，随任务运维授予。
- **查看员覆盖全部只读**：热词/任务/索引水位是健康巡检视角，供审计与值班。
- **矩阵上界 = 套餐**：角色授权前先在「套餐管理」勾选搜索引擎页面菜单（见 02 分册第七节）。

## 五、普通用户的搜索使用（无需任何 search 角色）

| 场景 | 口径 |
| --- | --- |
| 入口 | 基座顶栏搜索框（默认开启）+ 首页「全局搜索」卡片（添加卡片自主启用） |
| 鉴权 | 登录即可调用 `/search/api/*`，无权限码要求 |
| 能看到哪些源 | 会话租户目录内**已启用**且三层过滤全通过的源：用户持有源 `permissionCode`（超管 `*` 放行）+ 持有 `visibleRoles` 任一角色（若配置） |
| 能看到哪些文档 | 个人数据范围过滤后的文档（本人/本部门/本部门及以下/全部/共享给我；`visibleType=all` 公开文档全员可见） |
| 业务权限联动 | 源的 `permissionCode` 通常即业务工程的列表权限码（如 `oa:process:mine`）——用户在业务侧无该权限，搜索结果中也不会出现该源 |

## 六、数据权限（三层过滤机制详述）

与业务工程「行级 data_scope」不同，mse-search 的数据权限是**查询侧强制注入的三层漏斗**，不信任前端参数：

| 层 | 过滤内容 | 依据 |
| --- | --- | --- |
| ① 租户隔离 | 只在会话租户自己的目录（启用的源）与自己的索引（`{前缀}-{source}-{tenantId}`）上检索；`tenantId` 取自 TenantContext，缺失快速失败 | 租户上下文（强制，与角色无关） |
| ② 来源可见性 | `permissionCode`（不在用户权限集→整源不可见）+ `visibleRoles`（用户持有任一配置角色才可见）；两者同时生效、任一不满足即整源不可见 | Sa-Token 会话权限集 / 角色集 |
| ③ 个人数据范围 | 文档级：`ownerUserId`（归属人）/ `deptId`（归属部门）/ `visibleType=all`（公开）/ `visibleUserIds`（显式共享）；源开关 `dataScopeEnabled`（默认开，公告类无归属源可关——关闭时文档一律按公开落索引） | 复用底座 `@DataPermission` 五档语义与 `DataScopeResolverImpl` 合并算法（单体本地解析 / 微服务 RPC 解析，异常保守降级「仅本人」） |

补充规则：

- **操作权限 ≠ 数据可见性**：search 角色管的是「管理搜索系统」；普通用户搜什么由源级配置与业务权限码决定——两层互不替代。
- **防御纵深**：文档 `tenantId` 字段保留为防御过滤；扫描写入侧按当前扫描租户二次过滤；索引名操作校验前缀+租户后缀白名单。
- **可替换**：范围解析可声明自定义 `SearchDataScopeResolver` Bean 整体替换（含 RPC 版降级语义）。

## 七、种子落库情况

1. **角色：无种子（现状）**——`sys_role` / `sys_role_menu` / `sys_role_permission` 无任何脚本；租户管理员在基座「角色管理」按第二、三节**建议矩阵**手工建角色并授权即可（角色保存授权集合语义：传 null 保持不变、非 null 全量替换）。
2. **固化路径（规划）**：若需开箱即用，新增版本文件（如 `V{yyyyMMdd}_{NN}_search__roles.sql`，缺省 `-- mse-target: master`）按 code 判重插入角色、按 `(role_id, permission_id)` 判重绑定 4201-4211——随启动应用到业务主库并由租户库克隆/懒初始化通道就绪，免手工执行；**当前未落地，本文仅为规划输入**。
3. **菜单与权限点：已种子化**——属基座库全局表，走 `-- mse-target: base` 脚本（V20261001_01）由 starter-bridge 推送，幂等可重放（见 02 分册第一节）。
4. **无 sys_config 参数种子**——本工程运行参数全部在 `mse.search.*` 配置（Nacos/yaml），不占基座参数号段。
