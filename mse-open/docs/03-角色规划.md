# 03 角色规划 —— 角色定义、授权矩阵与数据权限

> mse-open 的角色与授权设计。权限点 id / code 见 [02-权限规划](02-权限规划.md)，功能点含义见 [01-功能规划](01-功能规划.md)。
> **本工程未随 jar 提供角色种子**（版本化脚本中无 `sys_role` 种子，开放平台管理建议收口给少数管理员，由使用方按需自建）——本文角色均为**建议角色**，落地时经基座「角色管理」创建并勾选权限点即可，无需改脚本。

## 一、角色模型说明

1. **双端会话（本工程特有）**：管理端接口同时接受租户端与平台端两种登录类型——**租户管理员**自管本租户的开放应用/API/凭证（绑定租户自动填充为本租户）；**平台管理员**治理平台域应用（tenantId=0 凭证，如给内网系统发的凭证）并可为应用绑定任意租户。
2. **超管不依赖角色**：租户超管（`sys_user.super_admin=1`）天然拥有套餐域内全量权限码；平台超管域内全量。开放平台功能点仅 12 个，小团队可直接用超管，无需建角色。
3. **角色受套餐裁剪约束**：即使授予建议角色，其权限也以租户套餐勾选的开放能力菜单（451-455）为上界（见 [02-权限规划](02-权限规划.md) 第七节）。
4. **开放 API 调用方不是"角色"**：第三方系统走机器凭证（appKey/appSecret + access_token + 应用授权 `open_app_api`），与基座人机角色体系完全隔离——接入方的"能调什么"由**应用授权**决定，不是角色。
5. **最小授权建议**：`open:app:reset-secret`（重置密钥）与 `open:app:grant`（API 授权）是高危动作，建议只授予管理员；审计岗位只给只读权限点。

## 二、建议角色清单（无种子，落地时创建）

| 角色（建议编码） | 名称 | 建议授予端 | 建议权限点 | 定位 |
| --- | --- | --- | --- | --- |
| `open_admin` | 开放平台管理员 | 租户端 | 7001-7012 全量 | 开放应用全生命周期、目录治理、审计，本租户开放域负责人 |
| `open_auditor` | 开放平台审计员 | 租户端 | 7001、7002、7009、7010、7011 | 只读：应用查询/详情、API 清单、调用日志、绑定关系——安全审计与对账 |
| `open_ops`（可选） | 平台开放运维 | 平台端 | 7001-7012 全量 | 平台域应用（tenantId=0）治理、跨租户应用绑定、平台目录启停 |

> 建议编码仅供参考（沿用 `mes_admin` / `oa_admin` 的 `<biz>_admin` 惯例）；创建路径：基座「角色管理」→ 新建角色 → 勾选「开放能力」分组下的权限点 → 授予用户。平台端角色在平台侧「角色管理」创建。

| --- | --- | --- | --- | --- | --- |
| 应用管理（451） | ● | ● | ▲（7001/7002） | ●（可绑任意租户） | ● |
| 调用日志（452） | ● | ●（7010） | ●（7010） | ● | ● |
| 身份绑定（453） | ● | ●（7011） | ●（7011，只读视图） | ● | ● |
| 接入指南（454） | ● | ● | ● | ● | ● |

设计要点：

- **启停与授权分离**：`open:api:status`（7012，目录启停）与 `open:app:grant`（7008，应用授权）是影响线上调用面的两个开关，审计角色一律不授。
- **凭证动作高危**：应用新增（7003，AppSecret 唯一展示时机）与重置密钥（7006）建议限定管理员个人操作，不进公共角色。
- **454 无权限点**：「接入指南」页随菜单组可见，作为管理员自助查阅的内置对接说明（与 docs/open-api-guide.md 同源）。

## 五、数据权限设计（平台端管理视角）

开放平台的"数据权限"由**三条边界**叠加，与人机角色的 data_scope 无关：

| 边界 | 规则 | 依据 |
| --- | --- | --- |
| 应用绑定租户（机器链路） | 应用必绑一个租户（0=平台域），开放 API 全部数据访问被租户插件约束在该租户域内——**凭证即数据边界**，接入方无法（也无需）传租户参数 | `open_app.tenant_id`，鉴权链注入租户上下文 |
| 会话世界（人机链路） | 管理端列表按会话世界隔离：租户会话查本租户应用/日志/绑定与租户目录副本；平台会话治理平台域（平台目录行 tenant_id=0、平台域凭证、跨租户绑定只读） | Sa-Token 双登录类型 + 目录真租户化 |
| 目录行级 | 每会话世界一份目录：租户端启停只影响本租户（副本行），平台端治理平台域行；rpc 条目扇出播种时各租户已调启停不被覆盖 | `open_api.uk_tenant_code` |
| 调用日志归属 | 日志带 tenant_id（0=平台域/未过 token 校验）；未过鉴权的 401 记录归平台域可见 | `open_api_log.tenant_id` |
| 身份绑定/扩展属性 | 租户表，基座租户插件行级自动隔离 | `open_user_bind` / `open_user_extend` |

补充两点人机侧口径：

- **高危动作不按数据范围切，按权限点切**：重置密钥、API 授权、目录启停没有"只读版"——要么能做要么不能做，所以审计岗位的隔离靠不授 7005/7006/7007/7008/7012 实现。
- **平台域应用（tenantId=0 凭证）**：数据访问不受租户插件行级过滤约束（平台世界），仅建议发给内网可信系统并强制开启请求签名 + IP 白名单。

## 六、种子落库情况

1. **无角色种子**：`sys_role` / `sys_role_menu` / `sys_role_permission` 不随 jar 播种——开放平台管理员少而权限集中，由实施/租户管理员按第二节建议在基座「角色管理」创建；后续若需要默认角色，新增 `-- mse-target: master` 版本脚本按 `code` 判重幂等插入。
2. **菜单与权限点**：属基座库全局表，走 `V20261001_01_open__open_base.sql`（头指令 `-- mse-target: base`）由 starter-bridge 推送 mse-system，就绪即推 + 周期重推自愈，免手工执行。
3. **业务表与 API 种子**：`open_*` 六张表 + 内置 API 种子（8001-8022）走 `V20261010_02_open__open_init.sql`（`-- mse-target: master` 最终态基线）随启动自动迁移；`open_app` / `open_api` / `open_app_api` / `open_api_log` 为全局表（已注册进租户插件白名单），`open_user_bind` / `open_user_extend` 为租户表。
4. **目录播种**：`V20261010_03_open__tenant_seed.sql`（`-- mse-target: master` + `-- mse-per-tenant: true`）把平台目录行按租户复制副本（副本 id = 源 id + 租户号低 8 位 ×1000，确定性生成），并同步改写本租户应用的授权指向——随租户初始化/懒初始化通道自动应用。
