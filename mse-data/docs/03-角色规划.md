# 03 角色规划 —— 角色定义、授权矩阵与数据权限

> mse-data 的角色与授权设计。权限点 id / code 见 [02-权限规划](02-权限规划.md)，功能点含义见 [01-功能规划](01-功能规划.md)。
> **重要：本工程无角色种子**——种子脚本只落子应用注册 / 菜单 / 权限点（`V20261001_01_data__data_base.sql`），`sys_role` / `sys_role_menu` / `sys_role_permission` 无任何 data 角色数据。本文角色均为**建议角色**（编码/名称/id 为建议值），由租户管理员在基座「角色管理」按需创建并授权。

## 一、角色模型说明

1. **全部为租户级角色**（`sys_role.tenant_id` = 当前租户）：数据中台是租户端子应用（side=1），不涉及平台端角色。
2. **租户超管不依赖角色**：`sys_user.super_admin=1` 的租户管理员天然拥有套餐域内全量权限码（含 data 全部 23 个权限点），可直接试用全部功能。
3. **角色受套餐裁剪约束**：即使建了管理员角色，其权限也以租户套餐勾选的 data 菜单（441-447）为上界（见 [02-权限规划](02-权限规划.md) 第六节）。
4. **建议角色是分工参考不是强制**：小型团队可只靠租户超管 + 一个「数据管理员」角色跑通全部链路；审批与开发职责分离的中大型团队按第二节的四角色方案落地。
5. **数据中台管理员 ≠ 租户超管**：data_admin 只管数据资产域，不涉及用户、角色、系统管理等基座能力。

## 二、建议角色清单（4 个，均为建议值）

| 角色 id（建议） | 编码（建议） | 名称（建议） | data_scope（建议） | 定位 |
| --- | --- | --- | --- | --- |
| 21 | `data_admin` | 数据管理员 | 1 全部 | 数据源、同步任务、依赖编排、质量规则、查询白名单，全模块管理 + API 审批兜底 |
| 22 | `data_approver` | 数据审批人（可选） | 1 全部 | 数据服务 API 的发布审批（职责分离场景单设；小团队可并入数据管理员） |
| 23 | `data_analyst` | 数据分析师 | 1 全部 | 概览、数据地图（元数据/血缘/采样/导出）、质量报告查阅、AI 问数 |
| 24 | `data_developer` | 数据服务开发者 | 1 全部 | API 定义/试运行/提交审批、调用方应用与授权管理、开放调用对接 |

> - **审批与提交天然分离**：提交审批用 `data:service:save`（9511），审批用 `data:service:approve`（9519）——两个权限点分属不同角色即可实现「开发者不能自己发布」。审批流可用 `mse.data.service.approval-enabled=false` 整体关闭（保存即发布，见 [05-配置手册](05-配置手册-零基础版.md)）。
> - data_scope 建议统一「1 全部」：数据中台内**无部门维度数据**（数据资产按租户隔离、不按部门切分），部门级 data_scope 在本工程无实际效果。
> - 角色 id 建议从 21 起避开 mes 的 11-19 惯例段；因无种子，实际 id 由基座「角色管理」新建时自动分配，无需登记 alloc-tables。

## 三、角色 × 模块授权矩阵（建议）

| 模块（menu_id） | 数据管理员 | 数据审批人 | 数据分析师 | 数据服务开发者 |
| --- | --- | --- | --- | --- |
| 数据概览（441） | ● | ▲ | ● | ▲ |
| 数据源管理（442） | ● | — | — | ▲ |
| 数据集成（443） | ● | — | ▲ | — |
| 数据地图（444） | ● | — | ● | ▲ |
| 数据服务（445） | ●（含审批） | ◐（仅审批） | — | ◐（无审批） |
| 质量监控（446） | ● | — | ◐（只读+报告） | — |
| 查询白名单（447） | ● | — | — | — |

设计要点：

- **写权限收归管理员**：数据源、同步任务、质量规则、查询白名单的编辑全部集中在数据管理员——这些对象是数据链路的「地基」，误改影响下游 API 与质量报告。
- **数据服务是唯一多角色协作域**：开发者建 API 与应用（无 `approve`），审批人放行发布（仅 `approve` + 查询），实现最小职责分离；`data_admin` 作为兜底持有含审批的全量。
- **分析师全程只读 + 导出**：元数据采集（`data:meta:collect`）归管理员——采集是链路动作；分析师拥有查询/采样/导出（`data:meta:list` + `data:meta:export`），满足「找数、看数、取数」。
- **AI 问数跟随地图权限**：mse-ai 智能体经 `data_query` 工具受控取数，工具侧校验租户与白名单，不单独消耗 data 权限点；能登录数据中台看地图的角色即可被授予问数智能体。

## 四、AI 问数授权（嵌入 mse-ai）

AI 智能查询无独立权限点（见 [01-功能规划](01-功能规划.md) 第八节）：mse-ai 侧建「问数」智能体并挂 `data_query` 工具，工具内自动完成租户过滤、白名单校验、SQL 防护与限行。授权方式：

| 事项 | 建议 | 说明 |
| --- | --- | --- |
| 智能体发布 | mse-ai 管理员创建并发布 | 工具 action：`meta_search` / `execute` / `datasource_list` |
| 使用者 | 数据分析师、管理层 | 在 mse-ai 对话工作台自然语言查数 |
| 可查范围 | `ods_` 贴源表 + 本租户白名单业务表（中台库通道） | 需要扩表时由数据管理员在「查询白名单」登记（须含 `tenant_id` 列） |
| 独立库租户 | 同上 | 白名单业务表自动路由至租户专属库；ods_ 与白名单混查被拒绝（提示拆分） |

## 六、数据权限设计

数据中台的隔离以**租户维度**为绝对边界，角色内不再做部门/个人切分：

| 场景 | 规则 | 依据 |
| --- | --- | --- |
| `dat_*` 十四张业务表 | 租户插件行级隔离（tenant_id），角色无关 | 多租户基线；换租户账号即看不到他租户的数据源/任务/API/应用 |
| 中台库通道取数（datasourceId=0） | 执行期自动注入 `tenant_id` 谓词（jsqlparser 改写，每张 JOIN 表都注入） | 物理共享表、逻辑租户隔离 |
| 外部数据源 | 数据源级隔离：仅本租户登记的数据源可用，不注入租户条件 | 数据源归属租户 |
| ODS 贴源表 | 动态建表自带 `tenant_id` 列；写入清理严格带租户条件，禁止 TRUNCATE | 引擎强制 |
| 查询白名单表 | 执行前在目标库探测须含 `tenant_id` 列，缺列拒绝执行 | 防无租户列表被共享查询 |
| 主库防呆（MasterDbGuard） | 外部数据源坐标命中平台主库一律拒绝（登记与执行双重校验） | 防绕过租户行级隔离 |
| 跨租户开放调用 | 签名调用只返回本租户行（同一套租户谓词注入） | 换租户 AppKey 调同一 API 结果隔离 |

## 七、种子落库情况

1. **已落地**：`data_base.sql`（mse-target: base）——子应用注册 id=6、页面菜单 440-447、权限点 9501-9523，starter-bridge 自动推送基座库（共享主库与各独立租户库各一份副本，分册账本 `mse_data_schema_history`），免手工执行。
2. **已落地**：`data_init.sql`（mse-target: master）——十四张 `dat_*` 业务表 DDL（无业务种子数据），随服务启动自动迁移（`mse.tenant.schema.auto-migrate=true`，失败阻断启动）；租户独立库经克隆 + 迁移通道自动就绪。
3. **未落地（本文为规划）**：角色与授权种子——`sys_role` / `sys_role_menu` / `sys_role_permission` 无 data 数据；租户管理员按第二、五节建议在「角色管理」手工创建。若后续版本补种子，应放 `data-service/src/main/resources/db/<方言>/` 新增版本文件（角色按 `code` 判重、绑定按 `(role_id, menu_id)` / `(role_id, permission_id)` 判重，已应用脚本不再修改）。
4. **菜单与权限点属基座库全局表**，与角色种子（租户库表）分离；本工程当前 base 脚本即全部基座接入内容。
