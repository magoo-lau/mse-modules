# 03 角色规划 —— 角色定义、授权矩阵与数据权限

> mse-fs 的角色与授权设计。权限点 id / code 见 [02-权限规划](02-权限规划.md)，功能点含义见 [01-功能规划](01-功能规划.md)。
> **重要口径：工程未随 jar 种角色**——`db/mysql/` 三个版本化脚本均无 `sys_role` / `sys_role_menu` / `sys_role_permission` 种子（fs 能力面小，5 个权限点，各租户按需自建即可）。本册全部角色为**建议角色（规划）**，落地方式见第五节。

## 一、角色模型说明

1. **全部为租户级角色**（`sys_role.tenant_id` = 当前租户）：fs 是租户端子应用（side=1），页面与权限点均在租户域（menu_scope=2）；平台侧无对应子应用与菜单。
2. **租户超管不依赖角色**：`sys_user.super_admin=1` 的租户管理员天然拥有套餐域内全量权限码——fs 仅 5 个权限点，**最小可用形态无需建任何角色**：套餐勾选 471 后，租户超管即可使用全部文件能力。
3. **角色受套餐裁剪约束**：即使授予文件管理员角色，其权限也以租户套餐勾选的 fs 菜单（471）为上界（见 [02-权限规划](02-权限规划.md) 第七节）。
4. **建议角色是起点不是终点**：租户管理员在基座「角色管理」按第二节清单自建角色并勾选权限点，可按岗位微调（角色保存授权集合语义：传 null 保持不变、非 null 全量替换）。
5. **业务模块消费不走角色**：oa 附件 / 用户头像 / 品牌素材 / 知识库等业务模块经 RPC 契约（api-fs）接入，走调用方登录态与上下文，不占用 fs 的页面权限点；fs 页面权限点只管「文件管理页」的人机操作。

## 二、建议角色清单（规划，工程未种）

> 角色 id 不做规划（alloc-tables 未约定角色号段，避免与各工程自建角色冲突）；下表编码为建议命名，落地时租户管理员自建即可。

| 编码（建议） | 名称（建议） | 授予权限点 | 定位 |
| --- | --- | --- | --- |
| `fs_user` | 文件用户 | 4101 查询 / 4102 上传 / 4103 下载 | 日常上传、下载、预览的业务人员——不含删除与迁移 |
| `fs_admin` | 文件管理员 | 4101-4105 全量 | 租户侧存储管理：删除清理、历史文件迁移、存储模式知悉 |
| `fs_viewer`（可选） | 文件只读 | 4101 查询 / 4103 下载 | 只读检索与下载（如审计、档案查阅岗），不可上传 |

平台侧（平台会话）：无角色种子与菜单；需要**全库迁移**能力时由平台管理员在平台角色管理中挂载权限码 `fs:storage:migrate`（4105，控制器 `@SaCheckOr` 双端校验），或直接由平台超管执行——详见 [01-功能规划](01-功能规划.md) 第六节。

## 三、角色 × 能力授权矩阵（按 5 个权限点展开）

图例：**●** 有权限　**—** 无权限

| 能力（权限点） | 租户超管 | fs_user | fs_admin | fs_viewer | 平台运维 |
| --- | --- | --- | --- | --- | --- |
| 文件查询 / 存储信息（4101） | ● | ● | ● | ● | —（平台无此页面） |
| 文件上传 / 大文件直传（4102） | ● | ● | ● | — | — |
| 文件下载 / 缩略图 / 直链（4103） | ● | ● | ● | ● | — |
| 文件删除（4104） | ● | — | ● | — | — |
| 存储迁移（4105，租户会话=仅本租户） | ● | — | ● | — | — |
| 存储迁移（4105，平台会话=全库） | — | — | — | — | ● |

设计要点：

- **删除收口在管理员**：删除是唯一破坏性操作（逻辑删元数据 + 尽力删物理对象），建议不授予普通用户；误传清理走文件管理员。
- **迁移是运维动作**：日常租户迁移（本租户范围）授 fs_admin；跨租户全库迁移只在平台会话执行——两类会话同码不同范围，控制器内按会话世界收口。
- **只读场景独立成角**：fs_viewer 满足「能查能下不能传」的档案查阅场景；如无此场景可不建。
- **业务模块不受此矩阵约束**：oa / 头像 / 品牌素材 / 知识库的文件读写随各业务模块自身权限走（见第一节第 5 条）。

## 四、数据权限（双层隔离）设计

fs 的数据隔离不依赖角色 data_scope，而是**双层硬隔离**（对所有角色一致生效，无法经授权穿越）：

| 层 | 规则 | 说明 |
| --- | --- | --- |
| 元数据层 | `fs_file.tenant_id` 行级隔离 | 租户插件自动过滤/填充；任何角色的跨租户 fileId 访问直接 404（先于权限校验的语义级隔离） |
| 物理层 | 存储键首段恒为租户 ID | local 目录 `{baseDir}/{tenantId}/` 与 rustfs 桶内 `{tenantId}/` 前缀互不可见 |
| 平台世界 | tenant_id=0 独立存放 | 平台会话上传（平台头像、域名个性化素材）落平台库 fs_file 副本；与租户数据物理分库 |
| 公开素材 | URL 首段租户号路由 | `/fs/asset/{tenantId}/{fileId}.{后缀}` 按段寻址，租户段与行 tenant_id 不符即 404；仅 access_level=public 行可达 |
| 存储迁移范围 | 随会话世界收口 | 租户会话仅迁移本租户文件；平台会话全库迁移 |

> 角色级 data_scope（全部/本部门/仅本人）在 fs 页面**不启用**：文件管理页是租户内共享存储视图（同一租户内互见，配合 bizType / 关键字检索）；如某租户需要「部门内互不可见」，属个性化定制（可经 `@ConditionalOnMissingBean` 替换 Service 实现），非基线行为。

## 五、种子落库情况（实际）

| 脚本（fs-service/src/main/resources/db/mysql/） | mse-target | 内容 | 角色相关 |
| --- | --- | --- | --- |
| `V20261001_01_fs__fs_base.sql` | base（基座库） | 子应用注册（id=8）+ 页面菜单（470/471）+ 权限点（4101-4105）+ 早期 NULL 挂靠补挂 | **无角色种子** |
| `V20261001_02_fs__fs_init.sql` | master（业务库） | `fs_file` 业务表 DDL | 无 |
| `V20261001_03_fs__fs_platform.sql` | base + platform 域（平台库） | 平台库 `fs_file` 自持副本 DDL（平台会话上传落 tenant_id=0 行） | 无 |

落库方式（免手工执行）：

1. base 脚本由 starter-bridge 就绪即推送 mse-system 按账本应用（周期重推自愈，幂等无害）；
2. master 脚本随服务启动自动迁移（`mse.tenant.schema.auto-migrate` 默认开启，失败阻断启动），租户独立库经克隆/懒初始化通道自动就绪；
3. platform 脚本随基座应用启动本地直建（单体/双库形态），微服务形态经 starter-bridge 推送 mse-system 应用到其主库。

**建议角色落地步骤（实施侧，对应 05 册第六节）**：租户管理员登录基座 →「组织管理 → 角色管理」新建 `fs_user` / `fs_admin`（可含 `fs_viewer`）→ 按第二节勾选权限点与 471 菜单 → 给用户授角色。平台侧全库迁移能力按第二节末段挂载。
